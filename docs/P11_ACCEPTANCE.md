# P11 — B2 Release Candidate Qualification, External Validation & C1 Gate Decision

Status: implementation complete; the current repository is **not yet B2 release-candidate qualified** because real external productive-language validation has not yet been admitted. P11.1 resolved the provider posture and P11.2 satisfies the P9 native-media portion of the gate.

## Purpose

P11 converts the B2 release process from a collection of operational tools into one explicit, auditable release-candidate decision.

It does **not** add C1 curriculum. It answers one product question:

> Has the B2 system accumulated enough repository, external-review, provider and regression evidence to justify opening a C1 product roadmap?

The answer is generated by code. No document or UI copy can override the gate.

## Hard dependency on P9

P11 imports and recomputes the P9 qualification model.

The C1 roadmap gate cannot open unless all P9 checks are green, including:

- B2 content breadth;
- real-world performance-bank breadth;
- licensed native connected-source depth;
- speaker/register/rate coverage;
- typecheck, tests, content validation, production build and certified E2E;
- offline, provider-outage and long-history resilience.

P11.2 now provides a provenance-audited `release/p9-native-inventory.json` that satisfies the native-media thresholds. P11 still recomputes P9 as a hard dependency, so future provenance drift or regression failure will close the gate again.

## External validation evidence

P11 adds `release/p11-external-validation.json`.

A qualifying external-validation set requires at least:

- one reviewer who is explicitly external to the project;
- reviewer role recorded as teacher, tutor or language professional;
- six representative productive artifacts;
- writing represented;
- spoken interaction or spoken production represented;
- a stable packet identifier and SHA-256 digest linking the review to the exported packet;
- no blocking reviewer issues;
- an approve or approve-with-notes verdict.

This evidence validates release quality and representative productive tasks. It does **not** certify the learner as CEFR B2 and it never modifies FSRS/mastery.

## Provider release profile and benchmark history

P11 adds `release/p11-provider-benchmarks.json`.

The release profile must be explicit:

- `offline-only`: no live coach/morphology provider is claimed in the release, so no fabricated benchmark is required;
- `connected`: every configured provider must have a latest passing benchmark run;
- `undecided`: blocks qualification.

For a connected provider, the latest run must:

- reference a declared provider;
- include a non-zero case count;
- pass every case;
- record p95 latency;
- verify the degraded/fallback path;
- finish with outcome `pass`.

This prevents a release from claiming live-provider capability without evidence, while also allowing a deliberately provider-free release profile.

## Release-candidate qualification engine

P11 adds `scripts/p11-release-candidate.mjs`.

Commands:

- `pnpm qualify:p11` writes P11 evidence without failing merely because the gate is blocked;
- `pnpm qualify:p11:strict` exits non-zero unless the full P11 release candidate is qualified.

The report composes:

1. the complete P9 release gate;
2. external validation;
3. provider release-profile/benchmark evidence;
4. the complete regression suite.

Generated artifacts:

- `artifacts/p11-release-candidate-qualification.json`;
- `artifacts/p11-release-candidate-qualification.md`;
- a machine-readable P9 qualification snapshot generated from the same run.

The final decision is one of:

- `OPEN_C1_ROADMAP`;
- `HOLD_B2_RELEASE_CANDIDATE`.

## CI and manual release workflow

Normal CI runs P11 in non-strict mode after the full regression suite. This validates the evidence manifests and uploads the current decision artifact while allowing ordinary development to continue when source-dependent release evidence is still missing.

The manual **P11 Release Candidate Qualification** workflow runs the full release suite and then invokes the strict P11 gate. It uploads evidence even when qualification fails.

This gives a release manager one authoritative workflow rather than requiring manual interpretation of separate P9, P10 and external-review outputs.

## How to qualify later

1. Export at least six representative B2 productive artifacts covering writing and speaking.
2. Have a real external teacher, tutor or language professional review that packet.
3. Admit the reviewer submission through the P11.1 cryptographic intake workflow so the exact packet SHA-256 and derived modality coverage are preserved.
4. Run the manual **P11 Release Candidate Qualification** workflow.
5. Open a C1 roadmap only when the generated decision is `OPEN_C1_ROADMAP`.

## Deliberate boundaries

P11 does not:

- fabricate native media;
- infer native-speaker status;
- self-attest external validation;
- convert teacher/tutor review into learner mastery;
- treat AI feedback as CEFR certification;
- open C1 because implementation work is complete;
- permit a UI flag or prose document to override the qualification engine.
